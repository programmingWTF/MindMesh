# 编码委派

## 为什么委派

**不要用「聊天」的方式写代码。**一个能读仓库、能跑测试、能自己迭代的编码 Agent，
比你在对话里逐行贴代码快一个数量级。

## 流程

### 1. 定义「完成」是什么

先写下**可验证的验收条件**：

```text
- [ ] <命令> 退出码为 0
- [ ] <测试> 全绿
- [ ] <行为> 在 <场景> 下正确
```

**没有验收条件的任务不要开始。**

### 2. 准备好上下文

- 目标仓库路径；
- 相关文件（**给它指路，不要让它自己 ls -R**）；
- 环境约束（版本、不能动的目录、代码风格）。

### 3. 委派

在你平台上用你有的方式（子进程 / 专门的编码 Agent / 后台任务）。
给它的指令里必须有：**目标、验收条件、边界（不许动什么）、以及「先读后写」**。

### 4. 验收（**这一步不能省**）

```bash
git -C <仓库> diff --stat          # 改了哪些文件
git -C <仓库> diff                 # 逐条看改动
<跑验收命令>
```

**逐条对照**你写下的验收条件。**不要**因为「看起来对」就通过。

### 5. 记录

在 `Memory/<我的名字>/` 里写：改了什么、为什么、怎么验证的、有没有遗留问题。

## 纪律

- **小步**：一次一个可验证的目标。大任务拆开。
- **先读后写**：让它先复述「你打算怎么改」，再动手。
- **不许动依赖目录**：`node_modules` / `vendor` / 生成产物。
- **不许自己提交到 main**：改动走分支 + PR。
- **不许把密钥写进代码**：用环境变量。

## 失败路径

| 症状 | 做法 |
|---|---|
| 它改了一大片无关文件 | 回滚，缩小任务范围，明确「只允许改 X 和 Y」 |
| 测试过了但行为不对 | 你的验收条件不够具体——补一个能测出该行为的用例 |
| 反复改不好同一个点 | 停止重试。**换思路**：可能是设计问题，先回来讨论 |
| 它说「做完了」但你没验证 | **永远自己验证**。「做完了」不是证据 |

## 验证

- 验收命令**真的跑过**，并且你看到了输出；
- `git diff` 里的每一处改动你都能解释为什么；
- 没有密钥、没有大文件、没有无关文件混入。
