# 为什么需要 MindMesh

## 一句话

**因为你会同时用好几个 Agent，而它们互相不认识。**

---

## 三个失败场景

### ① 失忆

你在 Claude Code 里花了半小时讲清楚「我的机器上装了什么、这个项目为什么不能动那个文件」。
第二天额度用完了，你换到 Codex。
**它什么都不知道。**你又说了一遍。

再换一个，再说一遍。

> 失忆的代价不是「重说一遍」，而是**每换一次 Agent，你的协作水平就退回原点**。

### ② 并行冲突

你让 A 记「这个项目的构建命令是 `pnpm build`」，让 B 记「构建命令是 `npm run build`」。
两个都写在同一个文件里。**谁是对的？什么时候变的？谁覆盖了谁？**

没有版本控制的多 Agent 记忆，本质上是一个**没有锁的共享内存**。

### ③ 上下文污染

上一个项目里，你告诉过 Agent「测试环境的 token 放在 X 文件，可以随便用」。
下一个项目里，它**理所当然地**去读了那个文件。

> 记忆共享的边界，本该由**目录**划清，而不是由 Agent 的自觉划清。

---

## MindMesh 的答案

三句话：

1. **把上下文放进一个 Git 仓库。** 版本控制天然给了你：历史、回滚、责任、差异。
2. **给每个 Agent 一块只属于自己的记忆区**（`Memory/<AgentName>/`），**剩下的全部只读**。
3. **任何操作的第一步都是 `git pull --rebase`**，包括你只是想读记忆。

### 为什么是 Git，而不是数据库 / API / MCP？

| 要求 | Git |
|---|---|
| 所有 Agent 都已经会 | ✅ **任何能跑 shell 的 Agent 都会 git** |
| 不需要常驻服务 | ✅ 只有一个远端 |
| 有历史、能回滚 | ✅ 原生 |
| 可离线、可审计 | ✅ 原生 |
| 权限可以按目录划 | ✅ 仓库权限 + 分支保护 |
| 引入成本 | ✅ 几乎为零 |

> **最省事的方案，往往是最好的方案。**
> 一个需要部署服务、维护索引、管理向量库的方案，**在你还只有两个 Agent 的时候就是负担**。

---

## 它不试图解决什么

- ❌ 不做检索排序（那是记忆引擎的领域，见 `Docs/Faq.md`）
- ❌ 不做 RAG / 向量库 / 知识图谱
- ❌ 不做 Agent 运行时、不做编排引擎
- ❌ 不做「自动记住」（记忆的写入仍然需要 Agent 主动做——但这只需要一条协议）

**它只做一件事：让多个 Agent 共享同一套记忆、技能和规则，而不打架。**

---

## 什么时候你不需要它

诚实地说，下面这些情况**别用**：

- 你只用**一个** Agent，而且不打算换；
- 你的上下文短到**一个 `AGENTS.md` 就装得下**；
- 你无法接受「记忆是明文文件」这件事（那就该去看加密方案，不是这里）；
- 你想要的是**开箱即用的产品**，而不是一个要被你自己改的架构。

> 这个项目更像一个**思维、一个方向、一个架构**，而不是一个不变量。
> 抄它的形状，比运行它的代码更有用。
