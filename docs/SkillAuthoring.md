# 让 Agent 帮你设计一个技能

> 技能不是文档，是**可执行的经验**。
> 这条流程既给人看，也直接给 Agent 看——*见 `Prompts/AuthorSkill.md`*。

---

## 判断：这东西该不该变成技能

按顺序问四个问题：

| 问题 | 若「是」 | 若「否」 |
|---|---|---|
| 1. 我**自己 Agent 原生**就会做吗？ | 不要写成技能，直接用原生的 | 继续 |
| 2. 会**重复用**吗？（≥3 次） | 继续 | 放 `Memory/` 就好 |
| 3. 别的 Agent 也会需要吗？ | 继续 | 放 `Memory/<你的名字>/` |
| 4. 有**明确的成功判据**吗？ | ✅ 写成 `Skills/<Name>/SKILL.md` | 先别写，等看清了再写 |

> **最常见的错误是第 1 条**：把平台自带的能力抄成一个技能，制造重复与漂移。

---

## 一个 SKILL.md 的结构

```markdown
---
name: <短横线命名，全局唯一>
description: <一句话：什么时候用它。要包含触发词，这是路由的依据。>
---

# <技能名>

## 什么时候用

<具体场景，最好带用户会说的原话>

## 前置条件

<需要什么：凭据 / 命令 / 权限 / 环境>

## 怎么做

1. <步骤>
2. <步骤>

## 命令 / 代码

```bash
<可直接复制的命令>
```

## 失败怎么办

| 症状 | 原因 | 做法 |
|---|---|---|
| <填> | <填> | <填> |

## 验证

<怎么确认成功了——**必须能验证**，否则这个技能不合格>
```

---

## 六条写作纪律

1. **description 决定它会不会被用到。**把**触发词**写进去（用户可能说的原话）。
2. **写「怎么做」，不写「是什么」。**背景最多两句。
3. **必须可验证。**给出「成功长什么样」。
4. **必须写失败路径。**没写失败处理的技能，等于只写了一半。
5. **不要藏密钥。**要凭据就写「去哪拿」，不要写值。
6. **尽量通用，实在不行就标注。**用相对路径、环境变量；平台专用的加 🔒 标记（见 `SkillsList.md`）。

---

## 安装第三方技能之前：先审

从任何市场/仓库拿来的技能，**都可能包含任意指令**。装之前至少看这四条：

| 检查 | 危险信号 |
|---|---|
| 它读什么 | 读取 ``` ~/.ssh ```、`.env`、浏览器 Cookie、凭据管理器 |
| 它发什么 | 向未说明的域名 POST 数据 |
| 它要什么 | 要求 `sudo`、要求关闭安全设置、要求 `--dangerously-*` |
| 它藏什么 | 混淆代码、大段 base64、从远端拉取脚本来执行 |

> 一句话：**技能是「会被你的 Agent 信任并执行」的东西，它的权限就是你的权限。**

---

## 提交

```bash
git checkout -b add-skill/<名字>
# 写 Skills/<Name>/SKILL.md
git add Skills/<Name>
git commit -m "add-skill: <名字>

Agent: <你的名字>"
git push -u origin add-skill/<名字>
gh pr create --fill
```

合并后记得更新 `SkillsList.md`（那也是一次 PR）。
