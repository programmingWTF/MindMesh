# FAQ

## 这跟「AI 记忆系统」是一回事吗？

**不是。**方向不同，而且是刻意的。

| | 记忆系统 / 记忆引擎 | MindMesh |
|---|---|---|
| 解决的问题 | **怎么把合适的记忆找出来**（检索、排序、压缩） | **多个 Agent 怎么共享同一套上下文而不打架** |
| 核心机制 | 向量 / 图 / 排序 / 摘要 | **Git + 单写者分区 + 协议** |
| 需要什么 | 索引、服务、有时要 API key | 一个 Git 远端 |
| 记忆的形态 | 常常是**不透明的块** | **明文文件**，你能 diff、能回滚、能直接读 |

两者**可以叠加**：MindMesh 负责「谁拥有什么、怎么共存」，检索层负责「怎么在里头找」。

> 如果你要的是检索与召回质量，去看成熟的内存引擎。
> 如果你要的是**多个 Agent 之间的秩序**，那是这里。

## 为什么不做一个数据库 / 服务？

因为有服务就有运维：启动、备份、升级、鉴权、端口。
**在你还只有两个 Agent 的时候，这些全是净损耗。**

Git 已经免费提供了历史、回滚、权限、离线与审计。

## 我需要几个 Agent 才值得用这个？

**两个。**

只用一个 Agent 时，你甚至不需要这个仓库——
一个 `AGENTS.md` + 一个 `MEMORY.md` 就够了。

## 记忆是明文文件，安全吗？

**取决于你的仓库是公开还是私有。**

- 私有仓库 + 每个 Agent 独立凭据 → 与你本机放文档同级；
- 公开仓库 → `Memory/` 就是**公开的**，请按「全世界都会看到」来写。

不要在里面放密钥（协议第 17 条）。要不要加密，是你的选择；本方案不做加密。

## 最多能接几个 Agent？

协议层面没有上限——**限制来自你的上下文预算**，不是仓库。

实践中的约束是：
- `Memory/<Agent>/` 目录越多，`Index.md` 越需要维护；
- `Skills/` 越大，越依赖「按需加载」的纪律。

## 记忆会无限膨胀吗？

会，如果不管理的话。建议：

1. **日志按天写**（`Daily/YYYY-MM-DD.md`），活跃状态单独维护在 `Memory.md`；
2. **长期结论才升到长期文件**，其余归档；
3. 定期跑 `Scripts/audit.sh` 看每个目录的体积与提交数。

## 为什么必须是「只写自己的目录」？让它们互相协作不行吗？

互相写必然导致冲突，而**冲突的语义是无法自动判定的**：
「A 说构建命令是 X，B 说是 Y」——工具无法知道谁对。

单写者分区把这个判断交还给**人类和 PR 流程**：

> 需要跨 Agent 共享的东西 → **提取成 `Skills/` 或顶层文档** → 走 PR → 有人拍板。

这看起来更麻烦，但它把「隐性冲突」变成了「显式决定」。

## 我能不用 Git 吗？

那这个方案就不成立了。**Git 是唯一的同步机制**，也是它对所有 Agent 通用的原因。

## 我能不能用它来共享非记忆的东西（比如配置、脚本）？

可以，而且推荐：

- 所有人要用的能力 → `Skills/`
- 所有人要知道的事实 → 顶层文档 / `06World.md`
- 只有某个人要用的 → 他的 `Memory/`

**判断标准只有一条：这条信息属于谁？**

## 统领 / 维护者必须是某个特定的 Agent 吗？

**不是。**只需要「能跑命令 + 能定时 + 能操作 Git」。

CI 是最省事的维护者——它不需要 Agent，也不需要机器。见 `docs/Orchestrator.md`。

## 我要贡献一个技能，怎么开始？

读 `docs/SkillAuthoring.md`，或者直接把 `Prompts/AuthorSkill.md` 丢给你的 Agent，让它来写。

## 这个项目的路线图是什么？

**没有强路线图。**它的形态应该由使用者的现实决定，而不是由维护者的想象决定。

如果你需要它变成别的样子：**fork 它，改它。**这正是它被写成文档而不是产品的原因。
